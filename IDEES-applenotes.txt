VERSIONS COMMERCIALES — STRATÉGIE (session 9)
Architecture : 3 fichiers dérivés du même code, features activées/désactivées par constantes.

Version PRO (en cours de construction)
→ Toutes les features : réglages, transposition, groupe de cordes, boucle élargie, sons personnalisables
→ Tous les patterns, toutes les étapes du Parcours
→ App payante (~4,99 €)

Version BASIC
→ Même contenu que la Pro, sans les réglages de transposition
→ App payante (prix inférieur à la Pro)

Version LIGHT / Gratuite
→ 5 patterns de l'Étape 1 × 3 directions (U/D/M) = 15 fiches
→ Tableau de progression simplifié : interprétation Pick ↑ uniquement
→ Pas de réglages avancés
→ Gratuite — vitrine d'acquisition

IDÉES RÉGLAGES — FAISABILITÉ ÉVALUÉE (session 9)
Envisager un onglet Réglages ou une modale ⚙️ dans le header (préférence : modale pour ne pas surcharger la nav).

1. GROUPE DE CORDES (DGBE / ADGB / EADG)
   → Changer le groupe de cordes sur lequel les patterns sont affichés et joués
   → Tab : remplacer les labels de cordes à la volée au rendu
   → Audio : décaler les notes MIDI de base selon le groupe sélectionné
   → Aucun impact sur la progression (clés basées sur les IDs patterns)
   → Faisabilité : facile à moyenne. Poids : quasi nul.

2. SONS PERSONNALISABLES POUR LA PREVIEW
   → Préréglages de timbre synthétique : "Épuré" (sinus), "Rond" (triangle), "Guitare" (dents de scie + filtre)
   → Zéro fichier audio chargé — tout en Web Audio pur
   → Faisabilité : facile. Poids : nul.
   → (Samples de vraie guitare = option future, alourdirait l'app)

3. DÉPART DE CASE PERSONNALISABLE
   → Actuellement fixé case 5 (retour case 6). L'utilisateur choisirait son départ.
   → Parser les numéros de cases dans l'ASCII tab et les décaler dynamiquement
   → Audio suit naturellement (parse déjà la tab)
   → Faisabilité : moyenne (parsing ASCII délicat mais propre). Poids : nul.

4. BOUCLE ÉLARGIE MULTI-POSITIONS
   → Exemple : 5→6, puis 7→8, retour 7→6, retour 5 — boucle sur plusieurs positions de manche
   → Générer dynamiquement une séquence multi-cycles dans le scheduler audio
   → Pédagogiquement très différenciant — unique sur le marché
   → Faisabilité : complexe mais dans l'architecture existante. Chantier dédié à prévoir.
   → Poids : nul (calcul temps réel, pas de données supplémentaires)

ARCHITECTURE — LIMITES ET CADRE (session 6)
- Plafond théorique : ~360 patterns (10 catégories × 12 patterns × 3 directions)
- En pratique : beaucoup moins, la curation est le vrai garde-fou
- Règle d'entrée d'un pattern : est-ce que ça entraîne un geste absent du dico ?
- Chaque catégorie a un nombre max de patterns (≈ 10-15) — au-delà = nouvelle catégorie
- Seuil technique pour séparer données/code : arrivée des catégories B et C
  → sortir les patterns dans un fichier patterns.json chargé au démarrage
- Les patterns "signatures" (style Hendrix, Govan, Wylde…) = motivation sans apprentissage de solo
- Mouvements essentiels vs facultatifs : à travailler ensemble pour définir le cœur du dico

PHILOSOPHIE — RAPPEL CLÉ
Le Dico Pattern reste zen et épuré : mouvement d'abord, musique après.
Pas de théorie, pas de notation, juste le geste qui devient inconscient.
Un futur outil séparé sera dédié à l'harmonie (ne pas mélanger les deux).
Priorité : le fond avant la forme. L'interface suit la pédagogie, pas l'inverse.


NOTE TECHNIQUE
La progression est sauvegardée localement sur chaque appareil.
Chaque élève sur son propre téléphone = progression 100% indépendante.
Pas de sync multi-appareils (pas prioritaire pour l'instant).
Modèle IA utilisé : Sonnet (suffisant pour le code — Opus pour la conception avancée).
Leçon session 3 : éviter les scripts Python sur le JS (fragile) — travailler directement dans le code.
Leçon session 4 : les nœuds Web Audio s'accumulent silencieusement si non déconnectés — toujours nettoyer dans onended.
Service Worker v15 — à incrémenter à chaque déploiement.
Leçon session 7 : boucle de clic indépendante de scheduleCycle — évite les race conditions de timing Web Audio. Chaque feature audio doit avoir son propre timer.
Leçon session 9 : apostrophes dans les options qBlock() cassent le onclick inline — toujours passer par data-attributes (data-qid / data-qval).
